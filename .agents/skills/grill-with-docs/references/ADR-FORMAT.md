# ADRの書式

> ワークスペースへの適用: 以下は原版の書式を訳したもの。既存のADR規約を優先し、このワークスペースでは正式ADRの作成に `adrs new`、作成・変更後の検証に `adrs doctor` を使う。下記の手動採番や最小書式で既存規約を置き換えない。

ADRは `docs/adr/` に置き、`0001-slug.md`、`0002-slug.md` のような連番を使う。
ディレクトリがなければ、最初のADRが必要になった時点で作成する。

## テンプレート

```md
# {意思決定の短い題名}

{背景、決定内容、理由を1〜3文で書く。}
```

ADRは1段落でもよい。価値があるのは欄を埋めることではなく、何を決め、なぜ決めたかを残すことである。

## 任意の項目

本当に価値を加える場合だけ記載する。多くのADRでは不要。

- **Status** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`）: 判断を見直すときに有用。
- **検討した選択肢**: 不採用の案を覚えておく価値がある場合のみ。
- **結果・影響**: 自明でない後続への影響を明示する必要がある場合のみ。

## 採番

原版では `docs/adr/` にある最大の番号に1を加える。このワークスペースではCLIと既存規約に従う。

## ADRを提案する条件

原版では次のすべてが必要。

1. **元に戻しにくい**: 後で変更するコストが無視できない。
2. **背景なしでは意外に見える**: 将来の読者がコードを見て「なぜこの方法なのか」と疑問を持つ。
3. **実際のトレードオフがある**: 現実的な代替案があり、理由を持って選んだ。

容易に戻せるなら戻せばよい。意外でなければ理由を疑問に思う人はいない。
現実的な代替案がなければ、「当然の方法を取った」以上に記録することはない。
ただし、既存規約が記録を要求する判断はこの3条件で除外しない。

## 該当する判断の例

- **アーキテクチャの形。** 「モノレポを採用する」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres への投影とする」。
- **コンテキスト間の連携方式。** 「Ordering と Billing は同期HTTPではなくドメインイベントで連携する」。
- **変更に大きな負担を伴う技術選定。** データベース、メッセージバス、認証基盤、デプロイ先など。すべてのライブラリではなく、入れ替えに四半期を要するほどのもの。
- **境界と対象範囲。** 「顧客データは Customer コンテキストが所有し、ほかはIDでのみ参照する」。明示的に行わないことも、行うことと同じくらい重要。
- **一般的な方法からの意図的な逸脱。** 「Xという理由でORMではなく手書きSQLを使う」。合理的な読者が逆を想定するような判断を残すことで、意図した設計が誤って『修正』されるのを防ぐ。
- **コードに表れない制約。** 「コンプライアンス上AWSを使えない」「連携先API契約により応答時間は200ms未満が必要」。
- **不採用理由が自明でない代替案。** 微妙な理由で GraphQL ではなく REST を選んだなら記録する。そうしなければ半年後に同じ議論が繰り返される。
