# CONTEXT.md の書式

## 構造

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するかを1〜2文で説明する。}

## 用語

**Order**:
{用語の意味を1〜2文で説明する。}
_避ける表現_: Purchase、transaction

**Invoice**:
納品後に顧客へ送る代金の請求。
_避ける表現_: Bill、payment request

**Customer**:
注文する個人または組織。
_避ける表現_: Client、buyer、account
```

## 規則

- **標準用語を選ぶ。** 同じ概念に複数の言葉がある場合は最適なものを選び、残りを「避ける表現」に記載する。
- **定義を短くする。** 最大1〜2文。その概念が「何をするか」ではなく「何であるか」を定義する。
- **このプロジェクトのコンテキスト固有の用語だけを含める。** タイムアウト、エラー型、ユーティリティのパターンなど、一般的なプログラミング概念は、頻繁に使っていても対象外。追加前に、固有概念か一般概念かを確認する。
- **自然なまとまりができたら小見出しで分類する。** 単一のまとまった領域なら平坦な一覧でよい。

## 単一と複数のコンテキスト

多くのリポジトリは単一コンテキストで、ルートに `CONTEXT.md` を1つ置く。

複数コンテキストの場合は、ルートの `CONTEXT-MAP.md` に各コンテキストの場所と関係を記載する。
以下は書式例であり、実在のファイルやイベントを示すものではない。

```md
# コンテキストマップ

## コンテキスト

- [Ordering](./src/ordering/CONTEXT.md): 顧客の注文を受け付け、追跡する
- [Billing](./src/billing/CONTEXT.md): 請求書を作成し、支払いを処理する
- [Fulfillment](./src/fulfillment/CONTEXT.md): 倉庫でのピッキングと出荷を管理する

## 関係

- **Ordering → Fulfillment**: Ordering が `OrderPlaced` イベントを発行し、Fulfillment が受信してピッキングを開始する
- **Fulfillment → Billing**: Fulfillment が `ShipmentDispatched` イベントを発行し、Billing が受信して請求書を作成する
- **Ordering ↔ Billing**: `CustomerId` と `Money` の型を共有する
```

適用する構造は次のように判断する。

- `CONTEXT-MAP.md` がある: 読んでコンテキストを特定する。
- ルートの `CONTEXT.md` だけがある: 単一コンテキストとして扱う。
- どちらもない: 最初の用語が確定した時点でルートの `CONTEXT.md` を作る。

複数ある場合は現在の話題が属するコンテキストを推定し、不明なら質問する。

## ローカル適用上の補足

ここでいうルートは主対象リポジトリのルートであり、複数リポジトリを格納するワークスペースのルートではない。
既存用語集に書式がある場合は、その書式を優先する。原版の `Language` と `_Avoid_` は、この訳では「用語」と「避ける表現」としている。
