# Interactive Flow Dashboard

## 目的と優先順位

ソースコードと開発管理情報を根拠として、実際の処理フローと開発進捗を同じ図に表示する。閲覧者が「何がどの順序で動くか」「開発・レビュー・検証はどこまで進んだか」「何が止まっているか」をすぐに確認できるようにする。

優先順位は **フローの正確性 > 進捗の根拠 > 操作性 > 装飾**。単なるカード型の進捗報告書に置き換えない。

ユーザーの元の依頼を保持したうえで、このSkillの可視化・操作・検証要件を追加する。開始点や終了点を固定せず、バッチ、API連携、非同期ジョブ、Webアプリなどに再利用できるようにする。

## 1. リポジトリとMR/PRの調査

1. 対象リポジトリ、基準ブランチ、開始・終了工程、成果物の保存場所を確認する。
2. 作業ツリーと現在のブランチを確認する。依頼に「mainをpull」とある場合、未コミット変更を破壊しないよう状況を確認してからfast-forward可能な更新を行う。安全にpullできなければfetchした追跡ブランチを基準にし、制約を明示する。reset、強制更新、stash、rebaseを無断で実施しない。
3. 関連するMR/PRの説明、差分、変更ファイル、レビュー、CI、マージ状態を調べる。GitLabのMRとGitHubのPRを区別する。
4. コードが存在すること、レビュー済みであること、mainへ反映されたこと、検証済みであることを別々に判定する。
5. 調査対象のリポジトリ、基準コミット、調査日時、取得できなかったMR/PRを記録する。
6. 前回の調査成果物がある場合、同一の基準・同一の工程定義かを確認したうえで、変更コミット・更新MR/PRを優先して差分調査する。影響が不明な箇所は再調査し、省略した範囲を明示する。

## 2. ソースコードに基づく処理フロー

- 起動条件、エントリーポイント、関数・サービス呼び出し、DB入出力、キュー、バッチ、外部API、結果保存まで追う。
- **ノード**は実在する処理工程、**エッジ**は順序・データ受け渡し・分岐条件を表す。
- 正常系だけでなく、確認できたリトライ、スキップ、例外、非同期処理、並列処理、終了条件を描く。
- それぞれの工程に実装ファイル、関数、コミット、関連MR/PRを紐付ける。1件のMR/PRが複数工程に影響するときは、該当するすべてのノードへ登録する。
- 未実装だが設計やMRで確認できる工程は点線などで区別する。未確認部分とコードで検証済みの経路を混同しない。根拠のない工程や接続は生成しない。
- フローが大きい場合は工程群をサブフローとして階層化し、必要に応じて展開できるようにする。

## 3. 工程ごとの進捗情報

各工程の状態は別フィールドに分け、情報がなければ「未確認」とする。

- 実装状態：未着手 / 開発中 / 実装済み / 未確認
- 統合状態：未マージ / レビュー中 / main反映済み / 未確認
- 検証状態：未検証 / 検証中 / 検証済み / 失敗 / 未確認
- 阻害要因：あり / なし / 未確認

ノードの表示色は上記の情報から一貫した基準で導き、凡例を表示する。**実装済みをそのまま完成扱いしない。** 開発状況と実際のバッチの稼働成功・失敗も混同しない。

全工程数、main反映済み、レビュー中、未完了、ブロック中の件数を示す。進捗率を出す場合は分母と完了条件を示し、不明な数値や日付を補わない。

## 4. インタラクティブHTMLの仕様

最初の画面に、対象システム、調査基準、進捗サマリー、処理フロー図、状態の凡例を置く。フロー図を主役にし、カードの羅列にはしない。

### フロー操作

- 処理の方向を統一してノード・エッジを配置し、矢印の交差と重複を抑える。
- ズーム、パン、全体表示への復帰、ノード選択を実装する。ノードのドラッグ移動を提供する場合は接続線も追従させ、配置のリセットを設ける。
- 選択した工程と前後の接続経路を強調し、関係の薄い要素を適度に弱める。
- ノードクリックでサイドパネルを開き、処理概要、入力・出力、条件、コード位置、実装・統合・検証の状態、課題、関連MR/PRを表示する。
- 複雑な工程はグループ単位で折りたたみ・展開できるようにする。
- フィルタや検索は利用者の確認作業に必要な場合に追加する。
- HTMLのMR/PRリンクは確認した実URLへ遷移できるようにする。調査報告ではMarkdown形式の [MR !123](https://example.com/) のようなリンクも記載するが、この例示URLを成果物へ流用しない。

### フロー再生

- 確認できた処理順序に沿った再生、一時停止、リセットを実装する。
- 現在ノードと接続経路を強調し、データが移動する様子は控えめに表現する。
- 分岐条件は見えるようにし、複数経路がある場合は利用者に選ばせるか代表経路であることを明記する。並列処理を逐次実行として偽装しない。
- **再生はコードの説明用シミュレーション**であり、実際の稼働監視・処理時間を示すものではない。実行中の状態と誤認するUIを作らない。

### 視認性とアクセシビリティ

- ダークテーマを基本とするが、状態色には一貫した意味を持たせる。
- ノードは短い工程名と重要状態を中心に表示し、詳細はサイドパネルへ移す。
- ホバー、選択、パネル開閉はおおむね150〜300msの自然な遷移を基本とし、常時動く派手な装飾を避ける。
- キーボード、フォーカス表示、文字コントラスト、狭い画面、prefers-reduced-motionに対応する。
- 再生・ズーム・展開などの操作は実際に機能するものだけを表示する。

## 5. モデル分担と下位モデルへのHTML実装委譲

**推奨構成：親エージェントはClaude Sonnet 5.5、HTML実装のサブエージェントはClaude Haiku系。** 利用可能なモデル名・バージョン・委譲ツールは実行時の環境で確認する。利用できないモデルや機能を仮定したり、実際には委譲していないのに委譲済みと報告したりしない。

### 親エージェント（Sonnet 5.5を優先）

- リポジトリ・MR/PRの調査、工程の抽出、分岐・依存関係の解釈、根拠確認、進捗判定を担当する。
- HTML実装担当へ渡す**確定済みデータ**を準備する。少なくともノードID、エッジ、条件、工程状態、根拠となるファイル・関数、MR/PR URL、表示要件、受け入れ条件を含める。
- 下位モデルの成果物をレビューし、実コードと画面の照合、操作・リンク・アクセシビリティの検証と修正方針の決定を行う。
- 調査を繰り返す場合は根拠のない再走査を避け、差分・キャッシュ・前回の結果を検証したうえで再利用する。

### 下位エージェント（Haikuを優先）

- **HTML/CSS/JavaScript/SVGのコーディング、ノード描画、画面レイアウト、アニメーション、操作イベント、見た目の修正を原則として担当する。**
- 与えられた工程・接続・状態・MR/PR URLをそのまま描画し、調査結果や進捗判定を独断で改変しない。
- 必要な機能やデータが不足する場合は推測で埋めず、親エージェントへ不足点を返す。
- 実装が複雑で手戻りが増える場合は作業を小さく分割する。親エージェントは必要に応じて実装方法を見直す。

下位モデルやサブエージェントが使えない環境では、その制約を明記して利用できる実装方法へ切り替える。**品質確認まで下位モデルに丸投げしない。**

## 6. 配布方式と安全規則

- ユーザー指定の技術・保存場所・配布形態を優先する。指定がなければ単一HTML（必要に応じてCSS/JavaScript/SVGを内包）を第一候補とする。
- xyflow / React Flowなどのライブラリは選択肢だが、単一HTML指定なら依存関係・ビルド成果物を含めて実際に動くことを確認する。
- フローのデータモデルと描画処理を分離し、将来の再調査でも更新しやすくする。
- リポジトリ内に秘密情報や内部URLがある場合は、公開HTMLや外部サービスへ無断で送信しない。外部CDNやリモート依存の導入は利用先の制約を確認する。
- ユーザーの承認なしに成果物を外部公開・push・PR/MR作成・マージ・デプロイしない。既存ファイルやローカル変更を無断で上書きしない。

## 7. 必須の検証

- コード上の処理順序、分岐、並列処理と図の全ノード・エッジを突合する。
- MR/PRリンクが実在するURLか確認する。権限等で検証できなければ「未検証」と明記する。
- ブラウザ検証が可能なら、PC/狭い画面で表示、ズーム、パン、全体表示、ノード選択、サイドパネル、再生・停止・リセット、分岐、リンクを操作する。
- 長い工程名、多数の工程、MR/PRのない工程、循環するフロー、未確認状態でも破綻しないことを確認する。
- 検証できなかった操作を「動作確認済み」と書かない。

## 8. 成果物と報告

1. 実際に操作できるHTMLと保存場所。
2. 調査対象、基準ブランチ、コミット、日時、調査上の制約。
3. 処理フローと進捗の短い概要。
4. 関連MR/PR一覧（実URLを使ったMarkdownリンク）、未完了・ブロック工程。
5. 実施した検証、未実施の検証、下位モデルへの委譲実績と制約。
