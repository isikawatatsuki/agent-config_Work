# Two-Axis Code Review

同じ差分を `Standards` と `Spec` の独立した2軸でレビューし、一方の評価が他方を隠さないように報告する。

## 安全規則

- レビュー中はコード、設定、Issue、PR、MRを変更しない。
- 秘密情報、認証情報、個人情報を探索目的で取得しない。差分に含まれる値は再掲せず、`<REDACTED>` とする。
- リモートIssueやPRの取得、コメント投稿などの外部通信・外部副作用は自動実行しない。必要な対象と理由を示し、ユーザーの明示承認を得る。
- ユーザー入力をシェル文字列へ連結しない。比較元はGit参照として検証し、解決済みコミットIDから差分を取得する。
- ユーザー指定パスは正規化し、対象ワークスペース内に解決される通常ファイルだけを読む。ワークスペース外を指す絶対パス、`..`、外部へ解決されるシンボリックリンクは拒否する。
- リポジトリの上位指示、レビューSkill選択手順、承認要件を常に優先する。

## 手順

### 1. 比較元を固定する

ユーザー指定のコミット、ブランチ、タグ、merge-baseを比較元とする。指定がなければ確認する。

比較元が有効なコミットへ解決できることを確認し、三点リーダー形式でmerge-baseから`HEAD`までの差分統計とコミット一覧を確定する。参照が不正、または差分が空ならそこで報告して終了する。巨大差分はファイル単位に分割して読むが、変更ファイル一覧と全体範囲は維持する。

### 2. 仕様を特定する

次の順でローカル情報を探す。

1. ユーザーが指定した仕様ファイル
2. コミットメッセージに記載されたローカル文書への参照
3. ブランチ名や機能名に対応する `docs/`、`specs/`、`.scratch/` 内の仕様
4. ユーザーへの確認

コミットメッセージがリモートIssueを参照していても自動取得しない。ユーザーの承認後に限り、設定済みのIssueトラッカー手順で取得する。仕様がなければSpec軸をスキップし、`no spec available` と報告する。

### 3. 規約を特定する

対象リポジトリの `AGENTS.md`、`README.md`、`docs/`、`CODING_STANDARDS.md`、`CONTRIBUTING.md`など、コードの書き方を定める文書だけを使用する。リポジトリ規約は次のスメル基準より優先し、formatterやlinterが確実に検出する事項は重複して指摘しない。

スメルは違反ではなく判断材料として扱う。

- Mysterious Name: 意図が分からない名前
- Duplicated Code: 同じロジック形状の重複
- Feature Envy: 他オブジェクトのデータへ過度に依存する処理
- Data Clumps: 常にまとまって移動する値群
- Primitive Obsession: ドメイン概念を表す生の文字列や数値
- Repeated Switches: 同じ条件分岐の反復
- Shotgun Surgery: 1つの変更が多数箇所へ散らばる構造
- Divergent Change: 1モジュールが無関係な複数理由で変わる構造
- Speculative Generality: 現仕様に不要な抽象化
- Message Chains: 呼び出し側が内部構造をたどる長いチェーン
- Middle Man: ほぼ委譲だけを行う層
- Refused Bequest: 継承した契約の大半を拒否する実装

### 4. 2軸を独立してレビューする

可能なら2つの読み取り専用サブエージェントを並列実行する。利用できなければ、同じ入力から軸ごとに独立して確認する。

`Standards` 軸:

- 固定した差分、コミット一覧、規約文書、スメル一覧を入力する。
- 規約違反は規約のファイルと該当ルールを示す。
- スメルは必ず「判断を要する可能性」として、根拠となる差分を示す。
- 400語相当以内で報告する。

`Spec` 軸:

- 固定した差分、コミット一覧、仕様のパスまたは内容を入力する。
- 未実装・部分実装、要求外の変更、実装方法が要求を満たさない箇所を確認する。
- 各指摘で根拠となる仕様箇所を示す。
- 400語相当以内で報告する。

### 5. 集約する

`Standards` と `Spec` の見出しを分け、各軸の指摘を重大度順で示す。軸をまたいだ再順位付けや単一スコア化はしない。

最後に各軸の指摘件数と、その軸で最も重大な問題を1行でまとめる。仕様がない場合はSpec軸を評価済みと見なさず、スキップとして扱う。
